Descripción del sistema

Guardia Digital Inteligente es una plataforma SaaS B2B de IAM/IGA (Gestión de Identidades y Accesos) desarrollada por Wayweb para el Mid-Market chileno. Aplica un enfoque Zero-Trust con MFA adaptativo, captura y normaliza los eventos de inicio de sesión, y detecta accesos anómalos para forzar re-autenticación o bloqueo.

La identidad se gestiona en Auth0 (Universal Login + Adaptive MFA). Los Log Streams de Auth0 se envían vía API Gateway → AWS Lambda (Node 20), que valida, normaliza y emite eventos estructurados a CloudWatch → Datadog (SIEM, pipelines y dashboard de compliance). Un job batch en Modal (cada 15 min) consulta un endpoint de Vertex AI para detectar anomalías de acceso (viaje imposible, fuera de turno, dispositivo nuevo) y cerrar el lazo de respuesta sobre Auth0.

La propuesta de valor se centra en tres ejes para el Mid-Market local: Zero-Trust sin la complejidad de un IAM enterprise; reducción de costo TI mediante una arquitectura 100% serverless (Lambda + API GW HTTP API + Modal); y cumplimiento de auditoría con trazabilidad completa de decisiones de acceso para la Ley 20.393.

2026-07-25 Sesión #7 Corrección: el lazo "automático" no lo era · 2 bugs reales encontrados y resueltos
La prueba que expuso que el ciclo programado nunca había funcionado solo, y su corrección real
La Sesión #6 declaró el lazo de respuesta como cerrado y automático, pero esa validación se hizo invocando detect_anomalies manualmente con datos ya preparados — nunca se había observado el job programado (el que corre solo cada 15 min, usando _fetch_pending_logs()) reaccionar sin intervención. Al probarlo de verdad —mandar un login anómalo real y esperar sin tocar nada— se descubrió que nunca había funcionado: la query a Datadog tenía un error que devolvía "0 logs" en absolutamente todos los ciclos, siempre, sin ningún error visible. Se corrigieron 2 bugs reales (más un tercero relacionado, causado por nuestra propia decisión de escalar a cero) y, al tercer intento, el lazo actuó completamente solo: detectó, clasificó y bloqueó una cuenta real sin ninguna intervención manual.

Bug 1 — la query de Datadog nunca encontraba nada

_fetch_pending_logs() filtraba por service:guardia-iam, asumiendo que ese era el facet de servicio de Datadog. En realidad "guardia-iam" es el valor de un campo anidado dentro de nuestro propio JSON (attributes.attributes.service) — el facet reservado service: de Datadog usa el valor que asigna el Forwarder desde el nombre real de la Lambda (guardia-auth0-webhook-staging). Cada uno de los ciclos programados desde la Sesión #6 imprimió "Ingesta Datadog: 0 logs" — literalmente siempre, sin ninguna señal de error.

Bug 2 — el campo timestamp colisionaba con un atributo reservado

El campo que handler.js emitía como timestamp choca de nombre con un atributo propio de Datadog, y llega de vuelta como una lista [iso, epoch_ms] en vez de un string — habría roto _hour_local_santiago() apenas se arreglara el Bug 1. Renombrado a auth0_timestamp, con manejo defensivo del caso lista de todas formas.

Bug 3 (relacionado) — cold-start del endpoint escalado a cero mataba el ciclo completo

Consecuencia directa de la decisión de la Sesión #6 de escalar Vertex a min_replica_count=0 para ahorrar ~$69 USD/mes: la primera predicción tras inactividad puede pegarle a un endpoint sin réplicas listas, y Vertex responde 429 Model is not yet ready for inference. El código no manejaba ese caso — la excepción tumbaba detect_anomalies completo, y como el cursor de Datadog ya se había confirmado antes de intentar la predicción, el evento quedaba perdido para siempre (el próximo ciclo nunca lo volvía a pedir). Se agregó reintento con backoff (hasta 8 intentos, 15s entre cada uno) y se movió la confirmación del cursor para que ocurra solo si la predicción tuvo éxito.

Bootstrap del backend remoto de Terraform (bucket S3 versionado/cifrado + tabla DynamoDB de lock, creados y verificados sin colisión con otros proyectos del portafolio). terraform apply real: 9 recursos creados (Lambda, API Gateway, IAM Role, CloudWatch Log Group). Webhook probado con curl real: 401 sin auth, 200 con auth válida.

Bug encontrado y corregido: el Log Stream de Auth0 ("Webhook personalizado") entrega el body como JSON Lines (un objeto por línea), no como un array JSON — handler.js solo sabía parsear un JSON único y habría fallado con 400 en cualquier batch de 2+ eventos. Se agregó parseLogBody() con soporte para ambos formatos, con 2 tests nuevos (11 en total), y se redesplegó.

Login real verificado end-to-end: se creó el Action Guardia Digital (post-login), se aplicó al flujo de Login, y se hizo un login real (wayweb.cl@gmail.com) que llegó normalizado a CloudWatch con geolocalización real (Santiago, Chile) — cumple el hito de Fase 2 del plan.

Modelo de IA: de dataset sintético a endpoint real en Vertex AI

Decisión de alcance: en vez de AutoML Tabular (mínimo ~1 hora y ~20 USD de presupuesto de entrenamiento incluso para datasets chicos), se optó por entrenar un RandomForestClassifier localmente (segundos) y desplegarlo en un contenedor de predicción propio sobre Vertex AI — más rápido y barato para validar el lazo completo.

Bug encontrado y corregido (pickle/joblib): la clase AnomalyScorer se serializó como perteneciente a __main__ (el script de entrenamiento), y el servidor de predicción no podía deserializarla (AttributeError). Se movió a un módulo compartido anomaly_scorer.py, importado por igual desde train_model.py y serving/serve.py.

Bug de permisos IAM: el Service Agent de Vertex AI no tenía permiso para leer la imagen desde Artifact Registry (FAILED_PRECONDITION). Se otorgó roles/artifactregistry.reader al service agent, a nivel de repositorio y de proyecto.

Error propio detectado y reparado: al actualizar el secret gcp-credentials en Modal con el VERTEX_ENDPOINT_ID real, se usó por error una variable vacía y se sobrescribió el JSON de credenciales con un valor en blanco. Detectado de inmediato; se generó una clave nueva de la misma cuenta de servicio vía gcloud iam service-accounts keys create, se reconstruyó el secret correctamente, y se borró el archivo temporal.

Validación final, con un usuario real: se ejecutó anomaly_detector.py contra el endpoint real de Vertex con el user_id real del login de prueba. Resultado: anomaly_score: 0.984 (patrón "fuera de turno" correctamente detectado) → _enforce_auth0_response() llamó a la Management API real → la cuenta quedó efectivamente bloqueada (blocked: true, verificado por API), y se desbloqueó después de confirmar.

ia_models/anomaly_detector.py — los 3 TODOs históricos, resueltos: _fetch_pending_logs() ahora consulta la Datadog Logs Search API v2 (con DD_API_KEY+DD_APP_KEY) y persiste el cursor de paginación en modal.Dict para no reprocesar logs entre ciclos de 15 min.
